# Development Flow

이 프로젝트는 AI 기반 9단계 앱 개발 방법론을 따릅니다.

## 기본 규칙

- 항상 한국어로 답변합니다. 사용자가 다른 언어를 명시할 때만 변경합니다.
- 앱 아이디어가 들어오면 9단계 플로우를 시작합니다.
- 각 단계 완료 후 사용자 확인을 받고 다음 단계로 진행합니다.
- 단계 산출물은 파일로 저장합니다.
- `PROGRESS.md`를 기준으로 현재 단계와 다음 할 일을 파악합니다.
- "이어서 하자" 요청이 오면 `PROGRESS.md`의 현재 상태에서 재개합니다.
- "멈춰", "여기까지", "stop here" 요청이 오면 현재 결과와 다음 할 일을 `PROGRESS.md`에 기록하고 중단합니다.
- 비용은 월 $0을 목표로 하며, BaaS와 무료 티어를 우선 검토합니다.
- v1은 핵심 기능만 포함하고, 미래 기능은 별도로 분리합니다.

## 9단계

| 단계 | 이름 | 산출물 |
|------|------|--------|
| 1 | 기획 초안 | `docs/planning/v1_기획안.md` |
| 2 | 기획 리뷰 | `docs/planning/v1_리뷰.md` |
| 3 | 기획 확정 | `docs/planning/FINAL_기획안.md` |
| 4 | 디자인 | `docs/design/` |
| 5 | 디자인 리뷰 | `docs/design/design_review.md` |
| 6 | 디자인 확정 | `docs/dev/개발의뢰서.md` |
| 7 | 개발 스펙 논의 | `docs/dev/개발스펙_논의록.md` |
| 8 | 개발 가이드 작성 | `docs/dev/` |
| 9 | 구현 | `src/` 또는 선택한 앱 구조 |

## 1. 기획 초안

포함 항목:

- 프로젝트 개요
- 핵심 기능: v1 범위와 향후 기능 분리
- 화면 와이어프레임: 필요 시 ASCII로 작성
- 기술 요구사항: 서버 비용 무료 티어 우선
- 데이터 모델
- 비기능 요구사항

## 2. 기획 리뷰

AI가 멀티 페르소나로 자율 리뷰합니다. 사용자가 각 페르소나 역할을 수행하지 않습니다.

| 페르소나 | 검토 관점 |
|----------|-----------|
| 사용성 전문가 | 흐름 불편, 단계 과다, 빠른 경로, 주요 액션 탭 수 |
| 가시성 전문가 | 중요 정보 강조, 우선순위/마감/상태 시각화, 빈 상태, 시각 계층 |
| 가독성 전문가 | 정보 밀도, 1/2차 정보 계층, 한 화면 과밀, 완료/보관 항목 처리 |

피드백은 `Red: 필수 수정`, `Yellow: 권장 수정`으로 분류합니다.

## 3. 기획 확정

- Red 전체와 타당한 Yellow 항목을 반영합니다.
- 반영 후 자체 검증 결과를 포함합니다.

## 4. 디자인

- 기본 디자인 기준점은 Figma MCP입니다.
- 선택지는 Figma, 코드 직행, 전체 디자인 플로우입니다.
- 사용자가 디자인을 건너뛰면 7단계 개발 스펙으로 이동합니다.
- Figma를 사용하는 경우 `docs/design/figma_reference.md`에 파일 URL, 주요 노드 ID/URL, 화면-코드 매핑을 기록합니다.
- 코드 직행을 선택하더라도 UI가 안정되면 Figma 반영 필요 여부를 사용자에게 확인합니다.

## 5. 디자인 리뷰

AI가 4개 관점으로 자율 리뷰합니다.

| 페르소나 | 검토 관점 |
|----------|-----------|
| UI/Visual 전문가 | 완성도, 색상/대비, 타이포그래피 계층, 간격/정렬/리듬 |
| UX/Interaction 전문가 | 흐름, 최소 44x44pt 터치 영역, 로딩/성공/오류 피드백, 내비게이션 |
| Consistency/Accessibility 전문가 | 폰트/색상/라운드 일관성, WCAG, 대비, 스크린 리더 고려 |
| Planning Alignment 전문가 | 기획 반영 여부, 기획에 없는 기능 여부, 화면별 기획 비교 |

누락 화면이 발견되면 `docs/planning/FINAL_기획안.md`도 함께 갱신합니다.

## 6. 디자인 확정

- 디자인 리뷰 피드백을 반영합니다.
- 필요하면 리뷰와 수정을 반복합니다.
- 개발의뢰서에는 구현자가 바로 이해할 수 있는 화면/상태/흐름을 정리합니다.
- 확정된 화면의 Figma 노드 정보가 `docs/design/figma_reference.md`에 최신 상태로 기록되어야 합니다.

## 7. 개발 스펙 논의

AI가 2개 관점으로 자율 논의합니다.

| 페르소나 | 검토 관점 |
|----------|-----------|
| 시니어 개발자 | 기술 스택, 아키텍처, 비용 최적화, 코드 품질 원칙 반영 |
| 서버 개발자 | Serverless vs BaaS, 무료 티어 범위, 데이터 구조, 인증 전략 |

반드시 포함:

- 기술 스택 표
- 데이터 구조
- 폴더 구조
- 구현 순서
- 예상 일정
- 비용 비교
- 무료 비용 체크리스트: Firebase Spark, Supabase Free, Cloudflare Workers Free 등

## 8. 개발 가이드

텍스트 처리, 색상/폰트, API 설계, 코딩 컨벤션 등 구현에 필요한 지침을 `docs/dev/`에 작성합니다.

## 9. 구현

권장 순서:

1. 프로젝트 설정
2. 모델
3. 순수 비즈니스 로직
4. Protocol/Interface
5. 서비스 구현
6. Store/ViewModel
7. 메인 UI
8. 상세 UI
9. 공통 컴포넌트
10. 통합

각 기능 구현 후 시니어 개발자 관점으로 자체 리뷰합니다.
