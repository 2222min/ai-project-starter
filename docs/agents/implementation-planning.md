# Implementation Planning

구현 전에 작업을 작고 검증 가능한 단위로 나눕니다.

## 적용 시점

- 기획/디자인/스펙이 승인된 뒤
- 여러 파일을 수정해야 할 때
- UI와 로직이 함께 바뀔 때
- 작업자가 바뀌어도 이어받을 수 있어야 할 때

## 계획 기준

- 정확한 파일 경로를 적습니다.
- 각 파일의 책임을 한 문장으로 적습니다.
- 한 작업은 독립적으로 이해되고 검증될 수 있어야 합니다.
- 불필요한 미래 확장은 넣지 않습니다.
- 기존 패턴을 우선 따릅니다.
- `TBD`, `TODO`, `나중에 구현` 같은 빈칸을 남기지 않습니다.

## 계획 템플릿

```markdown
# [작업명] 구현 계획

## 목표

- [한 문장으로 목표]

## 기준 문서

- 기획: `docs/planning/...`
- 디자인: `docs/design/...`
- Figma 참조: `docs/design/figma_reference.md`
- 개발 스펙: `docs/dev/...`

## 변경 파일

| 파일 | 작업 | 책임 |
|------|------|------|
| `path/to/file` | 생성/수정 | 이 파일이 맡는 역할 |

## 작업 목록

- [ ] 1. 실패 테스트 또는 검증 기준 작성
- [ ] 2. 최소 구현
- [ ] 3. 테스트/검증 실행
- [ ] 4. 문서/Figma 참조 갱신 확인
- [ ] 5. 자체 리뷰
```

## 자체 리뷰

- 요구사항을 빠뜨리지 않았는가?
- 한 작업에 서로 다른 목적이 섞이지 않았는가?
- 실제 검증 방법이 있는가?
- UI 변경이면 Figma 참조가 포함되었는가?
- 테스트가 어려운 구조라면 책임 분리가 부족한 것은 아닌가?
