# Workflow Harness

요청을 받으면 바로 코드로 뛰어들지 않고, 작업 성격에 맞는 규칙을 먼저 통과합니다.

## 적용 트리거

아래 요청이 들어오면 이 문서를 적용합니다.

- 새 기능 추가
- 기존 기능 수정
- UI/디자인 변경
- 버그 수정
- 리팩터링
- 테스트 추가
- 배포/PR/커밋 준비

## 하네스 선택

| 상황 | 먼저 확인할 문서 | 핵심 행동 |
|------|------------------|-----------|
| 아이디어/기능 추가 | `development-flow.md` | 9단계 플로우 시작, 기획/디자인 승인 후 구현 |
| 구현 계획 필요 | `implementation-planning.md` | 작은 작업 단위로 계획 작성 |
| 코드/UI 변경 | `change-management.md` | 문서 먼저, UI는 Figma 참조 확인 |
| Figma 또는 UI 변경 | `figma-code-reflection.md` | Figma, 문서, 코드 반영 상태 맞추기 |
| 기능/버그 구현 | `test-and-verification.md` | 가능한 범위에서 실패 테스트 먼저 작성 |
| 버그/실패 조사 | `debugging.md` | 원인 조사 후 최소 수정 |
| 완료 보고/커밋/푸시 | `test-and-verification.md` | 검증 명령 실행 후 결과 보고 |

## 기본 원칙

- 사용자의 명시 요청이 최우선입니다.
- 작업 전 관련 문서와 현재 상태를 확인합니다.
- 구현 전 기획/디자인/스펙 중 어느 문서가 기준인지 명확히 합니다.
- 여러 독립 변경은 분리합니다.
- 추측으로 고치지 않고, 근거를 확인합니다.
- 완료를 말하기 전에 방금 실행한 검증 결과를 확인합니다.
- 하네스가 과한 단순 문서 수정은 관련 문서만 갱신하고 종료할 수 있습니다.
